# cef_host.exe — браузер в отдельном процессе

Раньше весь Chromium жил прямо в `gta_sa.exe`: `libcef.dll` (~125 МБ), кучи главного процесса
браузера, кэши картинок и шрифтов и несколько копий кадра. Игре 32 бита, без флага 4 ГБ у неё 2 ГБ
адресного пространства. При сворачивании и разворачивании Chromium заново выделяет память под кадр
(на 3440×1440 это ~20 МБ одним куском). В раздробленной памяти куска не находилось, и Chromium
аварийно завершал игру: код **0xE0000008** (его «нехватка памяти»).

Теперь браузер — отдельный процесс `cef\cef_host.exe`, как `cef_host.exe` у Аризоны. В игре
остались только вывод картинки, ввод и связь с сервером; `client.dll` не загружает `libcef.dll`.

## Схема

```
gta_sa.exe                                       cef_host.exe (CEF, браузеры)
  loader → cef\client.dll                          │
     │  запускает при старте SA:MP, ──── канал ───►│  команды: создать/скрыть браузер, мышь,
     │  передаёт концы двух каналов   ◄── канал ───│  клавиши, события в JS, размер
     │                                              │  ответы: CEF готов, страница загружена,
     │                                              │  cef.emit / set_focus / hide из JS
     └─ общая память на браузер (кадр) ◄── пишет ──┘  OnPaint: изменившиеся области
                                                          │
                                                   renderer.exe (процессы страниц, как раньше)
```

* **Каналы** — два анонимных канала (в каждую сторону свой), сообщения `u32 длина + bincode`.
  Типы — `ipc/src/message.rs` (`ToHost`, `ToGame`, `Value`).
* **Кадр** — общая память на каждый браузер, её создаёт игра под размер окна
  (`Local\samp-cef-<pid игры>-<браузер>-<номер>`). Раскладка — `ipc/src/surface.rs`: заголовок
  64 байта (спин-блокировка, размер, «грязный» прямоугольник), дальше пиксели BGRA. Хост копирует
  в неё только изменившиеся области (и выпадающий список `<select>` поверх), игра раз в кадр
  забирает их в текстуру. Если блокировка занята — заберёт в следующем кадре, игра не ждёт.
* **Смена разрешения** — игра видит новый размер окна, создаёт новую общую память и шлёт `Resize`.
  Свёрнутое окно (0×0) размер не меняет.
* **Хост упал** — игра замечает обрыв канала, через 3 с запускает хост заново и пересоздаёт
  браузеры с теми же адресами. Игра закрылась (или упала) — каналы закрываются, хост выходит сам.
* **Плагины** (`cef\plugins\*.dll`, наш `core_cef.dll`) работают без изменений. Им по-прежнему
  передаётся `cef_list_value_t*`, но это своя структура с той же раскладкой поверх `Vec<Value>`
  (`client/src/list.rs`): null, bool, int, double, string. Подписчики `cef.emit` вызываются в
  потоке игры (раньше — в потоке CEF).

### Что исправлено попутно

* Движение мыши передаётся с флагами зажатых кнопок — в странице работает перетаскивание
  (`e.buttons`, обычные `<input type="range">`, выделение текста).
* Считается число кликов — работает `dblclick`.
* Кадр копируется только по изменившимся областям (раньше — весь кадр на каждую перерисовку).
* `cef_on_browser_ready` теперь действительно вызывает колбэк, когда страница загрузилась.

### Что убрано

Браузеры на текстурах объектов (`cef_create_ext_browser`, `cef_append_to_object`,
`cef_set_audio_settings`) и их 3D-звук: сервер Delirium их не использует. Команды от сервера
принимаются и игнорируются (в `cef_client.log` — сообщение).

## Файлы в игре

| Файл | Что это |
|---|---|
| `cef\client.dll` | игровая часть (без CEF) |
| `cef\cef_host.exe` | процесс браузера, новый |
| `cef\renderer.exe` | процессы страниц, как раньше |
| `cef\cef_host.ini` | необязательно: `render = auto / gpu / cpu`, см. «Видеокарта» |
| `cef\libcef.dll` и остальное CEF | без изменений, грузит их только хост |

Логи: `cef_client.log` (рядом с `gta_sa.exe`, игра), `cef\cef_host.log` (хост), `cef\cef.log`
(ошибки самого CEF).

## Сборка

На macOS/Linux — в Docker, ничего ставить не нужно:

```
scripts/docker/build.sh
```

Результат — `target/i686-pc-windows-msvc/release/`: `client.dll`, `cef_host.exe`,
`renderer.exe`, `loader.dll`.

* Образ — `scripts/docker/Dockerfile` (Rust, cargo-xwin, LLVM). Базовый образ берётся с
  `mirror.gcr.io`: Docker Hub из РФ отдаёт образы не всегда.
* Скрипт сам принимает лицензию Microsoft на CRT и Windows SDK (`XWIN_ACCEPT_LICENSE=1`),
  скачивает DirectX SDK (June 2010) и `libcef.lib` в `third_party/`. Первая сборка долгая
  (~1,5 ГБ загрузок), дальше — секунды: кэши в томах Docker `samp-cef-*` и в `third_party/`, `.xwin/`.
* Вместо `lld-link` из LLVM 14 подставляется `rust-lld` той же версии, что компилятор: старый
  линковщик не понимает экспорт `EXPORTAS`, который выдаёт свежий rustc.

На Windows — как раньше (`cargo build --release` с `CEF_PATH` и `DX_SDK`), плюс `-p host`.

## Проверка хоста без игры

`ipc/examples/host_smoke.rs` — запускает `cef_host.exe`, открывает тестовую страницу и проверяет
кадр в общей памяти, события JS ↔ игра, двойной клик, перетаскивание и выход хоста после закрытия
канала. Сборка (в контейнере, как `build.sh`):

```
cargo xwin build --release --target i686-pc-windows-msvc -p ipc --example host_smoke ...
```

Запуск на Windows из папки `cef` игры: `host_smoke.exe .` — в конце «ИТОГ: всё прошло»
и кадр в `host_smoke.bmp`.

## Связанное в asi-core (core.asi)

* **Флаг 4 ГБ** в `gta_sa.exe` (бит `IMAGE_FILE_LARGE_ADDRESS_AWARE` в заголовке PE) — без него
  игре 2 ГБ при любой раскладке. Раздаётся лаунчером вместе с игрой.
* **Звуки сервера** (`sounds.ini`) играют потоком с диска через свою копию `bass.dll` —
  `core_bass.dll`, её `core.asi` создаёт при запуске. В общем с SA:MP экземпляре BASS громкость
  потоков держится на нуле, поэтому раньше фоны и музыка грузились в память целиком (минута
  стерео ~10 МБ). Короткие звуки мутантов (`ped`) по-прежнему в памяти. В `sounds.log` —
  «Свой экземпляр BASS (core_bass.dll)»; если копия не поднялась, всё работает по-старому.
* **Тени объектов** (`CStencilShadows::RenderForObject`, 0x710310) выключены: на высоком качестве
  эффектов они падали на объектах с битой теневой сеткой (краш 0x710881).

## Замеры (3440×1440, 10–17 минут игры)

| | `gta_sa.exe` | отдельно |
|---|---|---|
| CEF в игре, без флага 4 ГБ | 1000–1050 МБ на старте, до 1300–1340 МБ; краши 0xE0000008 при сворачивании | render до 79 МБ |
| CEF в игре, флаг 4 ГБ | так же, крашей нет | |
| `cef_host.exe`, флаг 4 ГБ | до ~1230 МБ за 10 минут | render 68 МБ, хост ~10 МБ |

Рост памяти игры за сессию в основном не утечка: GTA заполняет кэш моделей до `stream.ini`
(`memory 256000` — 250 МБ).

## Видеокарта (`cef\cef_host.ini`)

```
render = auto   ; auto | gpu | cpu | shared
```

* `auto` (по умолчанию, и если файла нет) — Chromium рисует и собирает слои страницы на видеокарте
  в своём GPU-процессе. Если драйвер в его чёрном списке или GPU-процесс падает, он сам переходит
  на процессор.
* `gpu` — видеокарта, даже если драйвер в чёрном списке (`ignore-gpu-blocklist`).
* `cpu` — только процессор (`disable-gpu`, `disable-gpu-compositing`), как было, пока CEF жил в игре.
* `shared` — **на CEF 89 не работает** (ведёт себя как `auto`), заготовка под обновление CEF —
  см. «Кадр без копирования».

Режим пишется в `cef\cef_host.log` («отрисовка: ...»); чем Chromium рисует на деле, показывает
`host_smoke.exe` («отрисовка: ВИДЕОКАРТА — ANGLE (...)» или «ПРОЦЕССОР — SwiftShader»).

В любом из режимов кадр копируется: Chromium читает его с видеокарты в память (`OnPaint`), хост
копирует изменившиеся области в общую память, игра — в текстуру GTA (D3D9).

### Замеры (3440×1440, RTX 5060 Ti, игра ~95 к/с, перетаскивание карты)

Раз в 5 с: `cef\cef_host.log` — «кадры от CEF N/с, среднее X мс» (сколько кадров отдал Chromium
и сколько стоила их копия в общую память), `cef_client.log` — «кадры игры ...; в текстуру ...;
вывод ...; частота браузеров N».

| Шаг | Кадров/с | Стоимость |
|---|---|---|
| Игра | ~95 | — |
| Частота, заданная браузеру | ~95 | — |
| Chromium отдаёт (`auto`) | **~39** | копия в общую память ~5,2 мс (~4 Мпикс за кадр) |
| Игра забирает в текстуру | ~33 | ~1,9 мс |
| Вывод спрайта | ~95 | ~0,01 мс |

Узкое место — Chromium: в режиме с видеокартой он синхронно читает каждый кадр в память и ждёт
чтения, плюс ~5 мс нашей копии в его же потоке. Сторона игры не тормозит. `auto` против `cpu` на
глаз — «чуть плавнее»: отрисовку видеокарта ускоряет, а чтение кадра остаётся.

## Два хоста: современный (CEF 150) и совместимый (CEF 89)

С 2026-10-19 хостов два, игровая часть (`client.dll`) одна — от версии CEF она не зависит:

| | папка игры | CEF | кадр |
|---|---|---|---|
| современный | `cef-modern\` | 150 (`cef150`, `cef-sys150` — из апстрима ZOTTCE) | общая текстура D3D11 (`render = shared`), кадры по запросу хоста с частотой игры (`host/src/pacing.rs`) |
| совместимый | `cef\` | 89 (`cef`, `cef-sys`) | как раньше: Chromium читает кадр в память, до ~40–60 к/с |

* Сборка — один код хоста и рендерера, версия CEF — фичей (`legacy` по умолчанию, `modern` —
  `--no-default-features --features modern`, `--target-dir target-modern`), см.
  `scripts/build-client-win32.sh`. Дистрибутив CEF 150 скрипт скачивает сам в `third_party/cef150`.
* Выбор — `client/src/browser/engine.rs`: переменная `DELIRIUM_CEF_ENGINE` от лаунчера (галочка
  «Совместимый режим интерфейса») → `engine` в `cef\cef_host.ini` (раздаёт лаунчер — так всех можно
  вернуть на совместимый без новой сборки) → `auto`.
* Откат: современный не запустился, не прислал Ready за 20 с или упал дважды за 2 минуты —
  до конца игры совместимый, в `cef-modern\disabled.txt` — отметка с размером и временем
  `cef_host.exe` (обновится хост — попробуется снова). В `cef_client.log` — «интерфейс: ...».
* Оба хоста: приоритет на видеокарте выше обычного у хоста и GPU-процесса Chromium
  (`ipc/src/priority.rs` — интерфейс не дёргается, когда игра без лимита FPS грузит видеокарту на
  100%), `disable-gpu-vsync`, отключены изоляция сайтов, перевод и прочее лишнее, лимит кучи JS.
* Рукопожатие кадров: хост не просит у Chromium новый кадр, пока игра не забрала прошлый
  (`Surface::pending` — флаг `dirty` в заголовке общей памяти).
* `host_smoke.exe` лежит и в `cef-modern\`; в конце печатает «кадров интерфейса 1920x1080 с
  анимацией: N к/с» — так сравниваются хосты.

## Кадр без копирования (на будущее)

### Что не получилось на CEF 89

Режим `render = shared` (`host/src/gpu.rs`, событие `on_accelerated_paint` в крейте `cef`):
`window_info.shared_texture_enabled = 1`, Chromium отдаёт кадр общей текстурой D3D11, хост
открывает её (`OpenSharedResource`) на своём устройстве D3D11, копирует изменившуюся область в одну
из трёх промежуточных текстур и ждёт только эту копию на видеокарте (текстура Chromium действительна
лишь внутри вызова). Чтение в память и запись в общую память игры делает отдельный поток — Chromium
не ждёт. Выпадающие списки (`<select>`) читаются сразу.

Проверено 2026-10-05: на CEF 89 `OnAcceleratedPaint` **не вызывается** — кадры идут обычным
`OnPaint`, цифры как в `auto` (~39 к/с), ошибок D3D11 нет. Первая реализация общих текстур в CEF
(около версии 74) перестала работать примерно в 83–85, когда Chromium переделал вывод кадров (Viz);
поле `shared_texture_enabled` осталось, но ничего не делает. Рабочая поддержка вернулась в
**CEF 124+** (там `on_accelerated_paint` получает структуру `cef_accelerated_paint_info_t`
с NT-дескриптором текстуры вместо голого `shared_handle`).

### Как сделать: обновить CEF до 124+

Теперь это реально: CEF используют только `cef_host.exe` и `renderer.exe`, игровой `client.dll`
от него не зависит (обмен — крейт `ipc`, который от версии CEF не зависит). План:

1. Скачать сборку CEF (Spotify CDN, `cef_binary_<версия>_windows32` или `windows64` — хост может
   быть 64-битным: с игрой он общается каналами и общей памятью, разрядность не важна;
   `renderer.exe` — той же разрядности, что хост).
2. Перегенерировать `cef-sys/src/bindings.rs` (bindgen по заголовкам `include/capi`), поправить
   `cef-sys/build.rs` (`libcef.lib` новой версии).
3. Подогнать крейт `cef` под изменения API: поля `cef_settings_t` и `cef_window_info_t`,
   сигнатуры обработчиков (в т. ч. `on_accelerated_paint(..., info: *const
   cef_accelerated_paint_info_t)`), обёртки `rust_to_c/*`. `renderer` (V8: `cef.on/emit/...`) —
   то же.
4. В `host/src/gpu.rs` — открывать NT-дескриптор (`ID3D11Device1::OpenSharedResource1`) вместо
   `OpenSharedResource`; остальное (промежуточные текстуры, поток чтения) уже готово.
5. Заменить в сборке игры папку `cef` (libcef.dll и ресурсы, +~50–80 МБ), проверить `host_smoke`,
   затем игру; `render = shared` сделать значением по умолчанию, если работает.

Что ещё даст обновление: свежий Chromium (скорость, современные CSS/JS — сейчас в интерфейсе
нельзя, например, `color-mix`), CSS `zoom` по стандарту (уйдут расхождения координат мыши
в масштабированном интерфейсе — см. `RangeSlider.vue`, Leaflet).

Ожидание: карта с частотой игры (~95 к/с у пользователя с 160 Гц), выше частоты кадров GTA
интерфейс не обновится; задержка +1–2 кадра. Память игры не меняется — всё в процессах хоста.

### Что не годится

* Кадр текстурой сразу в GTA без чтения в память: GTA рисует через Direct3D 9, а открыть общую
  текстуру умеет только D3D9Ex — там нельзя managed-текстуры, на которых держится RenderWare.
* Отдельное прозрачное окно поверх игры (как оверлеи Steam/Discord): не работает в полноэкранном
  режиме, ввод придётся делить между окнами.
* Промежуточный вариант на CEF 89 — рисовать интерфейс в меньшем разрешении (например, 0,75)
  и растягивать в игре: пикселей ~вдвое меньше, кадров ~вдвое больше, но текст мягче. Не делали.
